从零到全貌：大数据架构

把大数据理解成一套“数据从哪里来 → 怎么进来 → 怎么流动 → 怎么计算 → 怎么存 → 怎么组织 → 怎么查 → 怎么治理 → 谁来使用”的系统工程。重点不是背框架，而是建立一套能自己推导架构的心智模型。

性能优化

OLTP vs OLAP：大数据世界的第一把钥匙

OLTP：业务交易系统

典型：MySQL、PostgreSQL、Oracle。服务“查一个用户余额、创建订单、扣款、更新订单状态”。特点是单条/少量数据、高并发、低延迟、增删改查、强事务。

SELECT * FROM user WHERE id = 123;
可以记：OLTP = 业务真相（Source of Truth）。
OLAP：分析系统

典型：ClickHouse、Doris、StarRocks、BigQuery、Snowflake、Redshift。服务“扫描几千万、几亿、几十亿行后做聚合”。

SELECT city, channel, count(*), avg(amount) FROM loan_application WHERE apply_time >= '2026-01-01' GROUP BY city, channel;
可以记：OLAP = 大范围扫描 + 聚合分析。
维度OLTPOLAP
典型任务交易、余额、订单、状态更新报表、趋势、聚合、行为分析
访问点查 / 小事务扫描大量行 / 少量返回
存储行式 + B+Tree 常见列式 + 排序 + 向量化常见
一致性通常更强很多场景可接受最终一致

数据链路与 Kafka

数据源
App/Web 埋点MySQLServer LogsIoT第三方数据
采集
SDK/APICDCFilebeat / FluentBit
消息
KafkaPulsar
为什么前端行为数据不直接写 MySQL

一个用户一次 App 使用可以产生几十到几百条曝光、点击、停留、滑动、错误、设备事件。千万级用户很容易变成数十亿事件。直接把这些事件逐条 INSERT 到业务 MySQL，会让交易系统承担本不该承担的高吞吐分析数据压力。

iOS/Web→埋点网关→Kafka
Kafka 的核心：可持久化、可回放、高吞吐的数据流日志

Topic 可以理解成数据频道，比如 user_behavior、loan_event、payment_event、risk_event、server_log。

Partition 是 Topic 内的分片，每个分区本质是一条有顺序的日志。横向扩展吞吐量依靠分区。

Kafka 只保证单个 Partition 内有序，不保证 Topic 全局有序。

同一用户如果需要保持顺序，通常把 user_id 作为 Key：

partition = hash(user_id) % partition_count

Offset 是消息在 Partition 中的位置。消费者记住“我读到哪里了”。

Consumer Group 让多个消费者并行消费不同 Partition。同一 Consumer Group 内，一个 Partition 同一时间只交给一个 Consumer。

Partition 数太少 → 并行度上不去；分区远多于消费者虽然可行，但会增加元数据与调度成本。
Replication / Leader / Follower / acks

Kafka Partition 通常有多个副本。Leader 处理读写，Follower 复制 Leader。Leader 挂掉后可以选新的 Leader。

acks含义权衡
0Producer 发出就算成功最快，风险最大
1Leader 写成功即返回可能在复制前丢失
all等待足够副本确认更安全，延迟更高
Retention / Replay / Log Compaction

Kafka 消费完并不等于消息立刻删除。可以按时间保留 7 天、30 天甚至更久，因此可以 Replay 重放历史数据。

Log Compaction 则是按 Key 保留较新值，例如 user123 的城市从深圳变上海，压缩后只保留新状态，适合状态主题、配置、CDC 类数据。

CDC：数据库变化怎么进入大数据平台

CDC = Change Data Capture。通过 MySQL Binlog 等捕获 INSERT / UPDATE / DELETE，而不是每隔几分钟全表 SELECT。

MySQL→Debezium / Flink CDC→Kafka

CDC 常携带 before、after、operation、timestamp，可用于重建数据库变化历史。

Schema Registry / Avro / Protobuf / JSON

Producer 与 Consumer 需要约定消息结构。Schema Registry 管理 Schema 版本与兼容性。JSON 好读但体积较大、解析慢、类型较弱；Avro / Protobuf 更适合高吞吐内部数据交换。

3

Flink 与流处理

Stream / Window / Event Time / Watermark

Flink 面对的是理论上“无限”的事件流，所以必须用 Window 把无限流切成有限范围。

窗口含义场景
Tumbling不重叠，例如 10:00-10:05、10:05-10:10每 5 分钟统计
Sliding窗口重叠，例如每 1 分钟算过去 5 分钟监控、风控趋势
Session根据用户无活动间隔切分用户行为会话

Event Time = 事件真实发生时间；Processing Time = Flink 实际处理时间。

Watermark 可以理解成“Flink 对事件时间已经推进到哪里”的判断。它允许系统容忍一定乱序与迟到。

Watermark = eventTime - 10 秒，意味着系统愿意等待约 10 秒的迟到数据。
State：为什么 Flink 不只是“流式 Map”

例如规则“一个用户 10 分钟内申请超过 5 次就标记异常”，Flink 必须记住每个用户过去发生了什么，这就是 State。

user123 = 4 user456 = 8

State 支持累计、去重、Session、Join、复杂事件分析、实时风控。State Backend 可以使用内存或更适合大状态的本地/嵌入式存储方案。

Checkpoint / Savepoint / Barrier

Checkpoint 定期保存 Kafka Offset + Operator State，用于故障自动恢复。

Savepoint 更偏人工触发，用于升级、迁移、变更并行度。

Checkpoint Barrier 是随数据流传播的特殊标记，用来形成一致状态快照。多输入 Operator 会涉及 Barrier Alignment。

某一路很慢会导致 Barrier 对齐等待、Checkpoint 变慢，并进一步产生 Backpressure。
At-most-once / At-least-once / Exactly-once
语义特点
At-most-once可能丢，但不会重复
At-least-once不丢，但可能重复
Exactly-once业务效果等价于只处理一次

真正的 Exactly Once 不是“网络绝不重复发送”，而是 Source、State、Sink 共同协作，让最终结果等价于一次。Sink 需要事务或幂等能力。

KeyBy / Shuffle / Parallelism

keyBy(user_id) 会确保相同 key 进入同一个下游 Subtask，本质是一次数据重新分区，也就是 Shuffle。

subtask = hash(user_id) % parallelism

并行度决定有多少 Subtask 同时工作，也决定状态如何分片。

Backpressure：下游处理不过来怎么办

如果 Kafka 每秒产生 100 万条，而 Flink 只能处理 80 万条，积压会越来越多。流系统通过背压让“下游慢 → 上游也慢一点”，避免内存无限增长直至 OOM。

Stream Join / State TTL / CEP / 去重

订单流和支付流不是同时到达的，因此 Stream Join 需要 State 暂存。State 不能无限增长，所以需要 Window / Watermark / TTL。

CEP（Complex Event Processing）可表达“5 分钟内登录失败 3 次 → 换设备 → 立即申请借款”这类事件序列。

事件去重常通过 event_id + State 实现，在一定 TTL 内记住已经看过的 ID。

分布式计算：Partition → Shuffle → DAG → Task

Map / Reduce / Shuffle

把 5TB 数据切成 100 份，每台 Worker 先本地计算，再把相同 Key 的结果重新分配到同一节点汇总。

Partition→Local Map→Shuffle→Reduce
Shuffle 是大数据系统最昂贵的操作之一：涉及内存、序列化、网络、磁盘、反序列化与重新计算。
Join 为什么贵 / Broadcast Join

两个大表按 user_id Join 时，必须把相同 user_id 的数据送到同一 Worker，通常触发大规模 Shuffle。

如果一边很小，例如 10MB 城市维度表，可以广播到每个 Worker，避免让 10TB 大表 Shuffle。

DAG / Job / Stage / Task

DAG 是计算执行蓝图：读取 → 过滤 → 投影 → Shuffle → 聚合 → 输出。

以 Spark 为例：

Job └─ Stage └─ Task

Shuffle 常成为 Stage 边界。一个 Stage 内通常有多个 Task 对不同 Partition 并行处理。

并行度与 Partition 数

Partition 太少，机器再多也用不上；Partition 太多，则产生大量 Task、调度开销与小文件。目标是“足够并行，但不过度碎片化”。

Data Skew：数据倾斜

如果 60% 数据都是 null，GROUP BY user_id 后所有 null 会挤到一个分区，导致某个 Task OOM 或极慢。

常见解决：

过滤异常 KeySalting 加盐Broadcast 小表局部聚合
RDD / Lineage / 容错

Spark 的 RDD = Resilient Distributed Dataset。Resilient 的关键之一在于 Lineage：记录数据是如何算出来的，某个分区丢失后可以按依赖链重新计算，而不必复制所有中间结果。

5

数据仓库：事实、维度、分层与建模

事实表 / 维度表 / 星型模型

事实表记录“发生了什么”：订单、借款、支付、金额、次数。维度表记录“从哪个角度看”：用户、城市、渠道、产品、设备、时间。

星型模型以事实表为中心，周围连接多个维度表。雪花模型则把维度继续规范化拆分，Join 更多。

宽表与反范式

分析系统通常读多写少，因此常用“用存储换计算”的策略，把用户、渠道、设备、产品等属性提前 Join 进宽表，减少运行时 Join 和 Shuffle。

ODS / DWD / DWS / ADS
层作用类比
ODS尽量保留原始数据原料
DWD清洗、去重、标准化、明细化处理好的食材
DWS用户日、渠道日、产品日等汇总半成品
ADS直接面向报表/应用做好的菜
数仓分层的本质：把重复计算提前做，让下游少 Join、少 Group By、少 Shuffle。
Bronze / Silver / Gold

这是另一套常见表达：Bronze ≈ ODS，Silver ≈ DWD，Gold ≈ DWS / ADS。本质仍然是“原始 → 清洗 → 面向业务的高级数据”。

粒度 Grain

事实表设计第一问不是字段，而是“一行到底代表什么”：一笔订单？一个用户一天？一次登录？

粒度不一致会导致 Join 后重复放大，比如一笔订单 Join 两条支付记录后，订单金额被重复 SUM 两次。
事务事实 / 周期快照 / 累积快照
类型含义例子
事务事实事件发生一次记录一次一笔借款、一次支付
周期快照固定周期拍一次状态每日余额、逾期天数
累积快照跟踪完整生命周期申请→审批→授信→借款→结清
SCD：慢变化维

SCD Type 1：直接覆盖，不保留历史。SCD Type 2：保留历史版本，常用 valid_from / valid_to / is_current。代理键 Surrogate Key 可用于表示同一业务 ID 的不同历史版本。

Kimball / Inmon / Data Vault

Kimball 强调事实表 + 维度表；Inmon 更强调企业统一数仓再到 Data Mart；Data Vault 强调历史、来源、变化与可扩展性，常见 Hub / Link / Satellite。

Data Mart / 主题域

大型企业通常按用户域、授信域、借款域、还款域、风险域、营销域、渠道域、财务域组织数据。Data Mart 是面向风险、营销、财务等部门的专题数据集市。

ETL / ELT / dbt / Airflow

ETL = Extract → Transform → Load；ELT = Extract → Load → Transform。云时代因为存储便宜、算力弹性，ELT 越来越常见。

dbt 管理 SQL 模型、依赖、测试、文档与版本；Airflow / Dagster / Prefect / DolphinScheduler 管任务 DAG、依赖、重试、回填与告警。

Backfill / Incremental / Idempotency

Backfill = 修复逻辑后重算历史；Incremental = 只处理新增或变化部分；Idempotency = 任务执行一次与执行多次，最终结果一致。

6

Data Lake / Lakehouse / Parquet / Iceberg

Data Lake：为什么出现

传统数仓擅长结构化数据，但企业还有 JSON、日志、图片、视频、音频、PDF、IoT、模型数据。数据湖的思想是：先把海量、多格式数据低成本存下来，典型底座是 S3/OSS/COS/GCS/HDFS。

Data Lake 更偏 Schema-on-Read；传统数仓更偏 Schema-on-Write。

Data Swamp：为什么裸数据湖会失控

如果只管“往湖里扔”，很快会不知道数据是谁的、字段什么意思、是否重复、是否可靠、能不能删、当前版本是什么。于是 Data Lake 可能变成 Data Swamp。

Lakehouse：湖的成本 + 仓的管理能力

Lakehouse 希望同时拥有：

对象存储低成本ACIDSchemaSQL多引擎版本治理

典型表格式：Iceberg、Delta Lake、Hudi。

Parquet：为什么大数据喜欢列式文件

Parquet = 列式文件格式。分析查询通常“很多行、少量列”，因此只读取需要列即可。

内部结构：

Parquet File ├─ Row Group │ ├─ Column Chunk A │ ├─ Column Chunk B │ └─ Column Chunk C ├─ Row Group └─ Footer Metadata

Footer 保存 Schema、Row Group 位置、min/max、null count、encoding、compression。查询引擎可跳过明显不匹配的 Row Group。

Iceberg：Table Format 到底是什么

Iceberg 不是数据库，它是在对象存储文件之上提供“表”的语义。

Table Metadata ↓ Snapshot ↓ Manifest List ↓ Manifest ↓ Parquet Data Files

可提供 Snapshot、Time Travel、Schema Evolution、Partition Evolution、Atomic Commit、Incremental Scan 等能力。

类比：S3 = 硬盘；Parquet = 文件格式；Iceberg = 表管理系统 + Git 风格版本管理。
Snapshot / Time Travel / Metadata

Snapshot 代表某一时刻表的逻辑状态。新增 C.parquet 后产生新 Snapshot；删除 B.parquet 也只是切换当前逻辑版本，旧数据可暂时保留，因此支持 Time Travel 与回滚。

Schema Evolution / Partition Evolution

Schema Evolution 允许表字段演进；Partition Evolution 允许分区策略从 day 改 hour 等，并让新旧数据共存而无需大规模重写。

Copy-on-Write vs Merge-on-Read
模式做法特点
Copy-on-Write更新时重写受影响文件写成本高，读简单快
Merge-on-Read先写增量/删除信息，读取时合并写快，读更复杂
Iceberg / Delta / Hudi
技术直觉优势
Iceberg开放、多引擎、大规模分析型湖仓
Delta Lake与 Spark / Databricks 生态紧密，ACID、流批统一
Hudi增量更新、Upsert、CDC 场景传统优势明显

三者能力正在大量重叠，真实选型要看生态、工具链、团队与工作负载。

Small File Problem / Compaction

大量小文件会导致 List/Open/Metadata/Task 调度成本爆炸，因此需要 Compaction 合并成较少的大文件。但文件也不能大到无法并行。核心是平衡文件数、并行度和更新成本。

Partition / Bucket

Partition 更偏业务裁剪，例如 date=2026-09-27；Bucket 更偏 Hash 分布，例如 hash(user_id)%64。前者用于减少扫描，后者有助并行与 Join 数据布局。

Storage / Table / Compute 三层分离
Storage Layer: S3 / OSS / GCS / HDFS ↓ Table Layer: Iceberg / Delta / Hudi ↓ Compute Layer: Spark / Flink / Trino

这就是现代 Lakehouse 的关键：存算分离、开放表格式、多引擎访问。

7

ClickHouse / Doris / StarRocks / MPP OLAP

ClickHouse 的定位

ClickHouse = 高性能列式 OLAP 数据库。擅长海量日志、用户行为、指标、事件流、时序与实时 BI。

关键机制：列式存储、压缩、向量化执行、排序组织、数据跳过、MergeTree。

MergeTree 与 ORDER BY

ClickHouse 中 ORDER BY 不只是“查询结果排序”，更重要的是决定磁盘上的数据组织方式，从而影响跳读与聚合效率。

ENGINE = MergeTree ORDER BY (event, ts)

ClickHouse 的 Primary Key 主要用于稀疏索引与数据跳过，并不等同 MySQL 的唯一主键约束。

为什么叫 MergeTree / 为什么不喜欢逐行 INSERT

数据写入会形成多个 Part，后台不断 Merge 成更大的 Part。逐行 INSERT 会产生大量小 Part，导致合并压力，因此更适合批量写入。

MergeTree 家族
引擎适合
MergeTree不可变事件、日志、埋点
ReplacingMergeTree版本替换 / 近似去重
SummingMergeTree数值预聚合
AggregatingMergeTree保存聚合状态
CollapsingMergeTree通过状态折叠表示变化
Materialized View / Pre-Aggregation

把经常重复的聚合在写入时提前算好，例如把 10 亿原始事件聚合成“每分钟 × 渠道”的几万行。查询从扫 10 亿行变成扫几万行。

预聚合不是越多越好，组合维度爆炸会增加存储和维护复杂度。
Doris / StarRocks

Doris 与 StarRocks 同样属于 MPP OLAP，常用于实时数仓、复杂 Join、BI、高并发报表、用户画像等。与 ClickHouse 能力重叠较大，真实选型应结合数据模型、实时更新频率、Join 复杂度、并发、延迟、运维和团队经验做 Benchmark。

MPP 是什么

Massively Parallel Processing：每个节点处理自己的一部分数据，再进行局部聚合、Shuffle、最终汇总。底层思想与 Partition / Task / Shuffle 一脉相承。

Shared-Nothing vs Shared-Data
架构特点
Shared-Nothing节点自己存自己的数据、本地盘延迟低，但扩容可能需要数据重平衡
Shared-Data多个计算节点共享 S3/HDFS 等存储，计算弹性更强，需要缓存和网络优化
8

Trino / Spark / SQL 查询优化

Trino 是什么

Trino = 分布式 SQL 查询引擎。它自己不一定保存数据，而是去 Iceberg、Hive、MySQL、PostgreSQL 等数据源查询。

类比：ClickHouse ≈ 高性能仓库 + 查询机器；Trino ≈ 跨多个仓库取货的超级查询团队。
Spark 是什么

Spark = 分布式大规模数据计算引擎，传统强项是 Batch、SQL、ETL、复杂 Join、历史重算、机器学习。现代 Spark 也支持 Structured Streaming。

Predicate Pushdown / Column Pruning / Data Skipping

只读取需要的列 = Column Pruning；把过滤条件尽量推到底层 = Predicate Pushdown；根据 min/max、索引、分区等直接跳过数据块 = Data Skipping。

Local Aggregate / Broadcast Join / Bucket Join

优化核心是减少网络和 Shuffle：本地先聚合后发送；小表 Broadcast；按相同 Hash 规则分桶可降低 Join 重分布成本。

Vectorized Execution

不是一行一行处理，而是一次处理一批值，更好利用 CPU Cache、SIMD、流水线。现代 OLAP 引擎普遍采用。

CBO / Statistics / Cardinality

Cost-Based Optimizer 根据表大小、行数、NDV、直方图、数据分布等选择 Join 顺序、算法、Shuffle 策略。统计信息错误会导致错误执行计划，例如误把十亿行表当成小表 Broadcast。

Bloom Filter

Bloom Filter 可以快速判断“某值肯定不存在”或“可能存在”，允许 False Positive，适合数据块跳过和快速存在性过滤。

查询慢排查顺序
扫描数据量太大？ → 分区裁剪生效吗？ → 只读必要列了吗？ → Filter 下推了吗？ → Shuffle 太大吗？ → 数据倾斜吗？ → Join 策略对吗？ → Statistics 准确吗？ → 并行度合理吗？ → 能否预聚合？ → 是否应该换 Serving 引擎？
9

Lambda / Kappa / Streaming Lakehouse / HTAP

Lambda Architecture

Batch Layer 保证最终正确性，Speed Layer 提供实时结果。优点是兼顾实时与历史重算；缺点是两套逻辑、两套代码、两套运维，容易出现语义不一致。

Kappa Architecture

所有数据都当成流，历史数据通过 Replay 重算。优点是链路更统一，复杂度较低；但并非所有离线场景都适合纯流式处理。

Streaming Lakehouse
Kafka→Flink→Iceberg→Spark / Trino

实时持续进入 Lakehouse，历史批分析也围绕同一份数据展开，减少传统 Lambda 两套数据与逻辑的割裂。

HTAP

HTAP = Hybrid Transactional / Analytical Processing，希望在一套逻辑系统中同时支持交易与分析。但 OLTP 喜欢小事务、随机读写、行存；OLAP 喜欢大扫描、列存、并行，因此很多 HTAP 实现底层仍是不同存储/执行路径。

Data Mesh / Data Fabric

Data Mesh 更偏组织与治理：Domain Ownership、Data as a Product、Self-Service Platform、Federated Governance。

Data Fabric 更偏技术整合：发现、连接、治理与自动化数据流。二者在现实产品宣传中边界会模糊。

Serverless Analytics

只提交 SQL 或任务，由云平台自动申请计算资源、执行、释放。适合峰谷明显的数据工作负载，但也有冷启动、成本不可预测、Vendor Lock-in 与网络成本问题。

Metadata / Catalog / Lineage

Metadata = 描述数据的数据，例如表名、字段、类型、负责人、来源、更新时间。

Data Catalog = 企业数据搜索引擎；Lineage = 数据从 MySQL → ODS → DWD → DWS → ADS → BI 的血缘关系，可用于影响分析与故障定位。

Data Quality / Observability

常见检查：Null Rate、Unique、Range、Row Count、Freshness、Consistency。数据可观测性常看 Freshness、Volume、Schema、Distribution、Lineage。

Job SUCCESS ≠ 数据正确。任务跑完但数据量少 80%，仍是事故。
Owner / SLA / Lifecycle

重要表应该有 Owner；例如 dws_daily_order 必须每天 07:00 前完成，这就是 Data SLA。不同数据也要有不同保留周期和自动归档/删除策略。

RBAC / ABAC / 行列级权限 / Masking

RBAC 按角色授权；ABAC 按属性授权；Row-Level Security 限制只能看本地区；Column-Level Security 限制敏感列；Masking 做脱敏。

Tokenization / Encryption / Audit

Tokenization 用 token 替换真实敏感标识并把映射单独保护；Encryption at Rest / in Transit 保护存储与传输；Audit 记录谁查了什么敏感数据、什么时候查、导出了多少。

高可用 / 容灾 / 备份

HA / RPO / RTO

HA = 节点故障后系统继续运行。RPO = 最多允许丢多少数据；RTO = 最多允许多久恢复。

Replica ≠ Backup

副本解决机器坏了，但如果误 DELETE，错误可能同步到所有副本。Backup / Snapshot / Time Travel 用来处理逻辑误操作与历史恢复。

为什么大数据系统默认机器会坏

机器、磁盘、网络、进程故障都属于正常事件，所以系统需要通过多副本、Checkpoint、重试、幂等、Leader Election、快照等方式构建故障恢复能力。

架构师视角：如何从需求推导技术

拿到需求先问 6 件事
  1. 数据量多大？每天新增多少？总量多少？单条多大？
  2. 产生速度多快？峰值 QPS / event rate 是多少？
  3. 结果延迟要求？10ms / 1s / 1min / 1h / T+1？
  4. 保存多久？7 天、1 年、7 年？
  5. 一致性要求？能否最终一致？
  6. 访问模式？点查、Join、聚合、全文搜索、向量检索、时序？

什么时候用 Kafka + Flink + ClickHouse

适合实时日志、实时行为分析、监控、报表、交易指标，要求秒级或更低延迟。

什么时候用 Kafka + Flink + Iceberg

适合实时进入数据湖、长期保存、后续批分析，即 Streaming Lakehouse。

什么时候用 Spark + Iceberg

适合复杂 Join、历史重算、ETL、机器学习，没有严格秒级实时要求。

什么时候用 Trino + Iceberg

数据已经在湖里，希望分析师直接 SQL 做 Ad Hoc 分析。

什么时候不用大数据

如果每天 100 万行、总数据 20GB，PostgreSQL + 定时任务 + BI 可能已经足够。不要为了“技术先进”堆 Kafka、Flink、Spark、Iceberg、Trino、ClickHouse。

完整案例：金融平台

假设：3000 万用户、500 万 DAU、20 亿行为事件/天、5000 万业务 DB 变化/天、历史保存 7 年、实时指标 < 5 秒、BI < 2 秒、历史分析 < 1 分钟。

iOS/Web ↓ Event Gateway ↓ Kafka ← CDC ← MySQL ↓ Flink ┌───────────────┐ ↓ ↓ ClickHouse Iceberg/S3 ↓ ├→ Spark Realtime BI └→ Trino

ClickHouse 存热数据，Iceberg/S3 存全量历史。实时与历史分析分别走更合适的 Serving/Compute 引擎。

题 1：最近 30 天实时行为分析，要求 1 秒级返回；历史 5 年数据偶尔查。你会怎么分层？
热数据：ClickHouse / Doris / StarRocks；全量历史：S3 + Iceberg + Parquet；实时链路：Kafka + Flink；历史 Ad Hoc：Trino / Spark。
题 2：为什么有了 Iceberg 还需要 ClickHouse？
Iceberg 解决的是湖上表管理与开放数据底座；ClickHouse 解决的是低延迟 OLAP Serving。存储统一，不代表所有查询负载都要用同一个执行引擎。
题 3：GROUP BY 很慢，优先排查什么？
扫描量、分区裁剪、列裁剪、谓词下推、Shuffle、数据倾斜、统计信息、并行度、能否预聚合。
题 4：Lambda 和 Kappa 最大区别？
Lambda 同时维护 Batch + Speed 两条链路；Kappa 尽量只保留 Stream 主链路，历史数据通过 Replay 重算。
