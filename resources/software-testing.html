1. 测试体系总览：测试到底在做什么

测试体系 = 在软件生命周期的不同阶段，用不同依据、不同粒度、不同技术手段，验证“系统是否做对了、做完整了、做稳定了、做安全了、做快了”。

软件测试本质上解决五个问题

  1. 功能对不对。
  2. 数据对不对。
  3. 系统之间协作对不对。
  4. 异常情况下还能不能工作。
  5. 上线以后扛不扛得住。

例如一个消费金融类业务主链路：

用户注册
↓
实名认证
↓
额度申请
↓
风控审批
↓
授信
↓
借款
↓
放款
↓
还款

测试绝不只是“点击申请额度，看页面有没有报错”，还要验证输入、参数、网关、鉴权、风控、数据库、Redis、消息、幂等、并发、故障、重试、数据一致性以及安全。

核心认知：测试是从用户界面一直延伸到数据、基础设施、依赖关系和生产运行状态的系统性验证。

2. 按测试层级划分：Unit → Component → Integration → API → System → E2E → UAT

flowchart BT
    A[Unit 单元测试]
    B[Component 组件测试]
    C[Integration 集成测试]
    D[API 接口测试]
    E[System 系统测试]
    F[E2E 端到端测试]
    G[Acceptance 验收测试]
    A --> B --> C --> D --> E --> F --> G

2.1 单元测试 Unit Test

测试最小代码单元：函数、方法、类、ViewModel、Service 方法、算法模块。核心要求是快、独立、稳定、可重复，并尽量不依赖真实外部系统。

数据库 → Mock
网络 → Mock
第三方 SDK → Mock
时间 → Mock
随机数 → Mock

如果一个 LoanService 测试必须真实连接数据库、风控和银行，那它已经不是严格意义的单元测试。

2.2 组件测试 Component Test

测试一个完整业务组件内部多个类、规则和模块的协作。例如“额度计算组件”内部可能包含额度规则、风险等级、产品规则、利率模型。关注点不是一个函数，而是一个可独立理解的组件。

2.3 集成测试 Integration Test

验证多个模块或服务组合后能否正确协作。常见问题包括字段命名不一致、协议不一致、事务边界问题、依赖配置问题。

单元测试：组件自己对不对
集成测试：组件之间能不能合作

2.4 接口测试 API Test

接口测试不仅看 HTTP 200，还要验证参数校验、认证、权限、业务规则、返回码、返回数据、数据库变化、幂等、重复提交、异常、超时和并发。

场景预期
amount=10000成功
amount=-1参数错误
amount 超出额度业务拒绝
userId 不存在用户不存在
重复 requestId不重复创建
token 过期401 / 指定鉴权错误

2.5 系统测试 System Test

验证完整系统是否满足需求。例如 App → Gateway → 用户 → 额度 → 风控 → 借款 → 支付的完整系统行为。

2.6 E2E 端到端测试

模拟真实用户完成完整业务链路，通常跨 App、Web、后端、数据库和第三方系统。优点是真实，缺点是慢、贵、易受环境影响、维护成本高。

2.7 验收测试 Acceptance / UAT

验证系统在业务上是否可以交付。通常由业务、产品或真实用户代表确认功能和规则是否满足预期。

2.8 测试金字塔

              UI / E2E
                 ▲
                / \
               /   \
              / API \
             /-------\
            /集成测试 \
           /---------\
          / 单元测试   \
         /_____________\

核心不是固定比例，而是：大量快速、稳定、低成本测试；较少昂贵、脆弱、跨系统测试。

3. 按测试目的划分：功能、性能、安全、可靠性、兼容性与恢复

3.1 功能测试 Functional Testing

验证系统是否按需求工作。常见测试设计方法包括等价类、边界值、判定表、因果图、状态迁移、场景法、错误推测。

3.2 性能测试 Performance Testing

Load Test

在预期负载下验证系统是否稳定，例如目标 5000 TPS。

Stress Test

不断增加压力直到系统达到极限，寻找崩溃点。

Spike Test

验证秒杀、热点等瞬间流量暴增场景。

Soak / Endurance

连续运行 24h、72h、7 天，发现内存、连接、线程等泄漏。

Capacity Test

确定最大用户数、连接数、订单量、数据规模等容量边界。

Scalability Test

验证横向/纵向扩容后性能是否按预期提升。

3.3 安全测试 Security Testing

覆盖认证、授权、敏感信息、输入攻击、漏洞、越权、重放、依赖风险等。典型问题包括 SQL Injection、XSS、CSRF、SSRF、IDOR、弱口令和 Token 问题。

3.4 兼容性测试 Compatibility

覆盖操作系统、浏览器、设备、分辨率、网络、数据库、SDK、客户端版本和 API 版本。

3.5 可靠性测试 Reliability

验证系统是否能够长期稳定运行，常关注 MTBF、MTTR、可用性和故障率。

3.6 容错测试 Fault Tolerance

主动制造 Redis、MySQL、MQ、服务、网络、磁盘等故障，验证降级、切换、重试、熔断和恢复行为。

3.7 混沌工程 Chaos Engineering

通过杀 Pod、断网络、增加延迟、制造丢包、模拟 AZ 故障来验证系统在真实故障下是否仍符合可靠性目标。

3.8 恢复测试 Recovery Testing

验证数据库、备份、日志、灾备等恢复能力，关注：

  • RTO：多久恢复。
  • RPO：最多允许丢多少数据。

4. 按软件生命周期划分：测试从需求开始，而不是从“测试阶段”开始

flowchart LR
    A[需求] --> B[设计] --> C[开发] --> D[构建] --> E[测试] --> F[发布] --> G[生产]

4.1 需求阶段

测试需求本身是否清晰、完整、无歧义。例如“密码错误多次后锁定”必须继续追问：几次？多久？连续还是累计？不同设备怎么算？验证码错误算不算？

4.2 设计阶段

评审架构、数据库、接口、安全、幂等、状态、事务和依赖设计。很多线上事故的根因其实是设计阶段没有明确。

4.3 开发阶段

执行 Lint、静态分析、代码审查、单元测试、组件测试，并在 CI 中失败即阻断。

4.4 联调阶段

重点做接口、契约、集成测试，验证 App、Gateway、服务和数据层的协作。

4.5 系统测试阶段

集中验证功能、异常、兼容、性能、安全和可靠性。

4.6 上线前

进行冒烟、回归、性能基线、安全扫描、发布验证和数据迁移演练。

4.7 上线后

通过灰度、Canary、Feature Flag、Synthetic Monitoring、RUM、Chaos 和生产监控继续验证。

4.8 Shift Left 与 Shift Right

Shift Left：尽早在需求、设计、开发发现缺陷。
Shift Right：上线后通过生产验证、监控、灰度、实验和混沌继续验证质量。

5. 变更相关测试：Smoke、Retest、Regression

5.1 冒烟测试 Smoke Test

只测试最核心路径，判断当前构建是否值得继续测试。例如登录、额度查询、借款、还款。

5.2 确认测试 Retest

针对已经修复的具体 Bug 再次验证该问题本身是否解决。

5.3 回归测试 Regression Test

验证修改没有破坏原本正常的其他功能。自动化测试价值最大的场景之一就是回归。

6. 静态测试、动态测试、黑盒、白盒、灰盒

6.1 静态测试

不运行程序，包括需求评审、设计评审、代码审查、Lint、SAST、静态代码扫描。

6.2 动态测试

运行程序并观察行为，包括 Unit、API、UI、Performance、Security 等。

6.3 黑盒测试

只关心输入与输出，不依赖内部实现。

6.4 白盒测试

知道代码逻辑并针对路径、分支和条件设计测试。

6.5 灰盒测试

掌握部分内部架构，例如数据库、Redis、MQ、接口，但不一定深入每个代码实现。企业中非常常见。

7. 测试依据：为什么要这样测

flowchart TD
 A[测试依据] --> B[需求]
 A --> C[设计]
 A --> D[协议/API Contract]
 A --> E[行业规范]
 A --> F[用户真实场景]
 A --> G[风险]

需求：定义业务应该做什么。
设计：定义系统如何实现，以及幂等、事务、状态等约束。
API Contract：定义字段、类型、范围、枚举、错误码。
标准规范：如 OWASP、行业安全规范、合规标准。
用户场景：如弱网、切后台、重复点击、网络切换。
风险：根据失败概率 × 影响决定测试深度。

8. 测试用例设计：如何从需求系统性推导测试空间

8.1 测试空间

完整测试空间至少包括：

输入空间
+
状态空间
+
环境空间
+
时间空间

8.2 等价类

把行为相同的一组输入划为一类，只选代表值测试，避免无意义穷举。

8.3 边界值

重点测试边界附近。例如范围 18～60，应关注 17、18、19、59、60、61。边界不仅是数字，也包括字符长度、日期、时间、数量和容量。

8.4 判定表

适合多个布尔条件组合，例如实名、年龄、风控、黑名单等组合业务规则。

8.5 因果图

强调条件之间 AND / OR / NOT 等逻辑关系，用于复杂规则系统。

8.6 状态迁移测试

适合订单、支付、贷款、审批、工单、物流、会员等生命周期业务。不仅测合法状态迁移，还要测非法迁移。

stateDiagram-v2
    [*] --> 待审批
    待审批 --> 审批通过
    待审批 --> 审批拒绝
    审批通过 --> 已放款
    已放款 --> 还款中
    还款中 --> 已结清

8.7 场景法

按真实用户链路组织测试，并重点加入断网、重试、刷新、杀进程、重复点击、超时等异常节点。

8.8 错误推测

依靠工程经验判断高概率 Bug 区域，例如 iOS 中的生命周期、异步回调、WebView、Token、页面重复跳转等。

8.9 Pairwise 两两组合

用于解决设备 × OS × 网络 × 语言 × 用户状态等组合爆炸问题。目标是让任意两个因素的组合至少覆盖一次。

8.10 覆盖率

包括需求覆盖、语句覆盖、分支覆盖、条件覆盖、路径覆盖。但必须记住：

Coverage ≠ Quality。覆盖率只能证明代码被执行过，不能证明逻辑正确。

9. 高级测试技术：探索式、TDD、BDD、Property、Mutation、Fuzz、Model-Based

9.1 探索式测试 Exploratory Testing

边测试、边学习、边设计下一步。它不是“瞎点”，而是围绕目标、风险和假设不断探索复杂交互。

9.2 Ad Hoc Testing

几乎没有结构和计划的临时测试。与探索式测试相比，系统性更弱。

9.3 Session-Based Testing

把探索式测试组织成固定时间的 Session，例如 60～90 分钟，明确目标、覆盖范围、发现和后续调查点。

9.4 TDD

Red → Green → Refactor

先写失败测试，再写最少代码通过测试，最后在测试保护下重构。价值不仅是测试，而是推动低耦合和可测试设计。

9.5 BDD

Given 用户已有额度
When 用户申请借款
Then 系统按业务规则处理

用业务语言连接产品、开发和测试。

9.6 ATDD

在开发前由业务、测试、开发共同定义验收标准。

9.7 Property-Based Testing

不是只定义输入和输出，而是定义系统应永远成立的性质，例如“余额不能为负”“同一个 requestId 最多产生一个结果”，再自动生成大量输入验证。

9.8 Invariant Testing

针对系统不变量进行验证，例如资金不能凭空产生、还款后本金余额不能增加。

9.9 Mutation Testing

自动故意修改代码制造错误，例如把 >= 改成 >。如果测试仍全部通过，说明测试检测能力不足。

9.10 Fuzz Testing

用随机、畸形、超长、非法编码、异常嵌套等输入轰击解析器、协议、接口和文件处理逻辑。

9.11 Model-Based Testing

先建立状态模型，再自动生成状态迁移测试，适合订单、支付、审批和协议。

9.12 Formal Verification

对于分布式协议、高可靠系统，可用形式化规范、Model Checking、TLA+ 等手段验证死锁、安全属性和状态可达性。

10. 自动化测试体系：不是 Selenium，而是一整套工程能力

自动化测试 = 测试代码 + 测试环境 + 测试数据 + Test Double + CI/CD + 报告 + 质量门禁。
flowchart LR
    A[Commit] --> B[Lint] --> C[Static Analysis] --> D[Unit Test] --> E[Build]
    E --> F[Component Test] --> G[Contract Test] --> H[API Test]
    H --> I[Integration Test] --> J[E2E] --> K[Security Scan] --> L[Release]

10.1 为什么 UI 自动化不能太多

UI 自动化依赖元素标识、动画、网络、后端、数据、设备性能等，非常容易形成 Flaky Test。

10.2 Test Double

类型作用
Stub返回固定答案。
Mock除了返回值，还验证调用次数、参数、行为。
Fake有简化版真实实现，例如内存数据库。
Spy记录真实调用供验证。
Dummy只是占位，不真正使用。

10.3 测试数据

避免长期共享账号。推荐 Setup → Test → Teardown，每个测试准备独立数据并负责清理。

10.4 环境

DEV → SIT → QA → UAT → PRE → PROD

不同公司命名会不同。PRE 重点是尽可能接近生产，用于配置、发布、性能和迁移演练。

10.5 Quality Gate

例如 Unit Test、Critical Security、API Regression、Build、Coverage 等指标不达标时禁止合并或发布。

11. 微服务、契约测试与服务协作

微服务测试复杂度主要来自依赖：

Loan Service
├─ User Service
├─ Risk Service
├─ Payment Service
├─ Redis
├─ Kafka
└─ MySQL

11.1 推荐测试结构

Service Unit
↓
Component
↓
Contract
↓
Integration
↓
E2E

11.2 Contract Testing

防止双方各自单测都通过，但接口契约已不兼容。例如 Consumer 期待字段 limit，Provider 改成 creditLimit。

11.3 Consumer-Driven Contract

Consumer 声明自己依赖哪些字段和行为，Provider 每次发布前验证自己仍满足这些契约。

11.4 API Schema Testing

除了值，还要验证字段存在、类型、nullable、范围、枚举和格式，通常基于 OpenAPI / JSON Schema。

11.5 API Version Testing

测试 v1、v2、v3 的前向和后向兼容，特别是移动端老版本客户端长期存在时。

12. 分布式系统测试：真正重点是“失败时仍然正确”

12.1 超时 Timeout

测试下游从 100ms 变为 500ms、3s、10s，验证调用方是否有合理 Timeout，是否留下半成品状态。

12.2 重试 Retry

验证重试次数、退避策略以及重试是否引发重复业务。

12.3 熔断 Circuit Breaker

验证 Closed → Open → Half-Open → Closed 的状态切换，避免持续打击故障服务。

12.4 降级 Fallback

次要服务失败时系统是否可以返回默认值或隐藏模块，而不是拖垮核心业务。

12.5 Bulkhead 舱壁隔离

验证某一模块流量爆炸时，是否耗尽全局线程池、连接池等共享资源。

12.6 Backpressure

生产速度大于消费速度时，系统是排队、拒绝、限流还是丢弃。

12.7 Rate Limit

测试阈值边界、返回码、Retry-After、用户级/IP级限流以及公平性。

12.8 服务发现

实例挂掉后是否及时摘除，流量是否停止发送到故障实例。

12.9 故障矩阵 Failure Matrix

故障点应验证
Gateway 超时客户端重试是否安全
Risk 超时申请不重复、状态可恢复
DB 写失败事务和补偿
Payment 超时不重复放款
MQ 发送失败Outbox / 重试 / 补偿
Redis 故障明确降级或失败路径
关键规律：单体系统更关注“功能正确”；微服务系统更关注“协作正确”；分布式系统更关注“失败时仍然正确”。

13. 幂等、并发与重复请求

真实系统中的重复请求可能来自用户连续点击、网络超时、App 重试、Gateway 重试、服务重试、MQ 重投。

13.1 幂等测试

对同一个 requestId 连续或并发发送多次请求，验证：

  • 数据库只产生一条有效业务记录。
  • 关键下游不会重复执行危险操作。
  • 消息不会形成重复业务结果。
  • 最终状态唯一。

13.2 并发竞争

例如同一用户同时发 10 个不同 requestId，但业务要求只能有一个审批中申请，则应验证最终只有一个进入流程。

13.3 可测试的实现机制

包括 Redis 分布式锁、数据库唯一索引、CAS、乐观锁、版本号等。测试需要针对锁过期、持锁服务崩溃、锁提前释放和高竞争设计异常场景。

14. 数据库、事务、迁移、精度与对账

14.1 数据库测试

覆盖 Schema、Migration、Constraint、Transaction、Index、Consistency。

14.2 事务测试

故意让事务中间某一步失败，验证前面的数据是否正确回滚或由一致性机制恢复。

14.3 Schema Evolution

测试增加列、删除列、改字段类型、索引、约束，以及新旧服务并存时的兼容性。

14.4 数据迁移

旧系统迁往新系统时必须验证数量、金额、关键字段、关系、异常记录、重复记录和缺失记录。

14.5 Reconciliation 对账

金融、支付等系统要验证内部账、渠道账、外部账差异发现和补偿机制。

14.6 Precision Testing 精度

测试金额小数、Decimal、整数分、四舍五入、截断、累计误差和利息计算，避免浮点误差。

14.7 Backup / Restore

备份成功不代表可恢复。必须定期真正恢复，验证恢复时间和数据完整性。

15. Redis / Cache / MQ 专项测试

15.1 Redis 与缓存

  • 缓存命中与失效。
  • 缓存穿透。
  • 缓存击穿。
  • 缓存雪崩。
  • TTL。
  • 分布式锁。
  • 缓存与数据库一致性。
  • Redis 故障后的降级。

15.2 MQ

  • 消息重复。
  • 消息丢失。
  • 消息延迟。
  • 消息乱序。
  • 消费失败。
  • 重复消费。
  • 消费者重启。
  • Broker 故障。
  • 消息积压。

15.3 重复消息

相同 eventId 投递多次，业务结果仍应只发生一次。

15.4 乱序

例如 Approved → Cancelled 的正常顺序被反转，需要通过 version、sequence、状态机等保证结果正确。

15.5 DB 成功、MQ 失败

这是经典分布式一致性场景，需要验证 Outbox、补偿任务、消息重放、重试和最终一致性。

17. 安全测试与 DevSecOps

17.1 客户端安全

逆向、敏感数据、本地存储、证书校验、调试、越狱/Root 环境等。

17.2 API 安全

认证、授权、越权、重放、参数篡改、限流、错误信息泄露。

17.3 横向越权

修改资源 ID 后访问其他用户数据，例如修改 loanId / userId。

17.4 纵向越权

普通用户调用管理员能力。

17.5 服务端安全

SQLi、SSRF、RCE、依赖漏洞、错误权限、Secret。

17.6 SAST / DAST / IAST / SCA

类型含义

DAST运行系统后从外部攻击。
IAST结合运行时与内部信息。
SCA分析第三方依赖和开源组件漏洞。

17.7 Secret / Supply Chain

检查 API Key、Token、Private Key 泄露，以及依赖、构建流水线、镜像、Artifact、签名、SBOM 等供应链风险。

19. Web 与移动端专项测试

19.1 Web

  • 组件测试。
  • 页面功能测试。
  • API 测试。
  • 跨浏览器测试。
  • Visual Regression。
  • Accessibility。
  • Web Performance：LCP、INP、CLS、TTFB。

19.2 移动端生命周期

前台 → 后台 → 锁屏 → 恢复；测试请求、Timer、页面状态、Token、异步回调。

19.3 杀进程

支付或借款进行中杀 App，重启后应基于服务端真实状态恢复，不应简单假设失败。

19.4 权限

相机、照片、定位、通知、麦克风等都要覆盖允许、拒绝、永久拒绝、设置重新开启。

19.5 弱网

高延迟、低带宽、丢包、断网、Wi-Fi / 4G / 5G 切换。

19.6 安装与升级

首次安装、覆盖安装、重新安装、空间不足、v1→v2、v1→v3、本地 DB、Keychain、UserDefaults、缓存和登录态迁移。

19.7 Crash / Memory / Energy

关注 Crash-Free Users、Crash-Free Sessions、内存增长、CPU 和后台能耗。

20. 容易遗漏的专项：时间、国际化、无障碍、易用性

20.1 时间测试

覆盖时区、UTC、本地时间、跨天、月末、年末、闰年、2 月 29 日、夏令时、Clock Skew。

20.2 Localization 与 i18n

覆盖语言、日期、货币、数字格式、RTL、字符长度、复数规则。i18n 更偏系统设计能力，Localization 更偏具体语言版本验证。

20.3 Accessibility

测试 VoiceOver / Screen Reader、焦点顺序、动态字体、对比度、键盘操作、Accessibility Label 和 Traits。

20.4 Usability

“按钮能不能点”属于功能测试；“用户知不知道应该点哪个按钮”属于可用性测试。

21. 发布、生产验证与渐进式交付

21.1 数据库升级

测试 ALTER 对锁表、耗时、旧代码兼容和回滚的影响。

21.2 Rollback

必须认识：代码回滚 ≠ 数据回滚。新版本已经写入新数据结构时，回退旧代码可能直接不兼容。

21.3 Canary

1% → 5% → 20% → 50% → 100%

逐步放量并观察错误率、Latency、Crash 和业务指标。

21.4 Feature Flag

代码已部署，但功能通过开关逐步开放。

21.5 Dark Launch

新系统接收真实流量，但结果不影响用户，用于性能与稳定性验证。

21.6 Shadow Traffic

复制生产请求到新系统，不返回结果给用户，用于新旧系统结果比对。

21.7 A/B Test

验证产品假设和转化差异，不是传统意义上的缺陷测试。

21.8 Synthetic Monitoring

上线后定期自动模拟用户完成关键链路，验证服务仍然可用。

21.9 RUM

真实用户监控，关注真实网络、加载时间、错误和 Crash。

22. 测试与可观察性 Observability

现代测试体系离不开：

Logs
Metrics
Traces
Profiles

测试失败时，理想状态应能通过 TraceId、requestId、service、latency、error 快速定位 Gateway、服务、DB、Redis、MQ 或第三方依赖。

22.1 SLO

如果系统目标是 99.95% 可用性，测试和架构验证应判断系统是否具备达到该目标的能力。

22.2 Error Budget

当错误预算消耗过快时，团队可能暂停高风险发布，转而优先提高可靠性。

22.3 SRE 与测试

传统测试更偏发布前；SRE 更偏生产持续可靠性。现代 Quality Engineering 会把两者逐渐打通。

23. 软件质量模型与架构质量属性

可以把质量理解为：

  • 功能适合性。
  • 性能效率。
  • 兼容性。
  • 易用性。
  • 可靠性。
  • 安全性。
  • 可维护性。
  • 可移植性。

测试和架构的关系是：

架构设计
↓
定义质量属性与目标
↓
测试策略
↓
验证质量属性是否实现
架构师视角：测试不是独立于架构的活动，而是架构质量属性的验证机制。

24. Verification、Validation 与 V 模型

24.1 Verification

“我们是不是把系统做对了？”主要关注实现是否符合规格、设计和要求。

24.2 Validation

“我们是不是做了正确的系统？”主要关注最终产品是否真正满足用户和业务需求。

24.3 V 模型

开发阶段对应测试活动
需求验收测试设计
系统设计系统测试设计
架构 / 概要设计集成测试设计
详细设计 / 模块设计单元测试设计

重点不是图形本身，而是强调测试设计和开发阶段同步进行。

25. 软件测试经典原则

  1. 测试只能证明缺陷存在，不能证明绝对没有缺陷。
  2. 穷尽测试不可能。
  3. 越早测试，发现和修复成本越低。
  4. 缺陷通常聚集在少数模块。
  5. 杀虫剂悖论：同一组测试长期重复执行，发现新缺陷的能力会下降。
  6. 测试依赖上下文：金融、电商、游戏、医疗的风险重点不同。
  7. 无错误谬误：没有已知 Bug 的产品，也可能不是用户真正需要的产品。

26. 可测试性 Testability：好的架构应该容易测试

如果业务逻辑直接依赖真实数据库、网络和时间，就很难测试。更好的设计通常通过接口和依赖注入隔离外部依赖。

LoanService
↓
LoanRepository Interface

生产：
MySQLLoanRepository

测试：
FakeLoanRepository

可测试性与模块化、低耦合、清晰接口、稳定状态机、可观察性高度相关。

27. 测试数据、测试环境与 Service Virtualization

27.1 测试数据原则

可重复
可隔离
可清理
可追踪
不使用真实敏感数据

27.2 Synthetic Data

优先生成合成数据，而不是复制真实身份证、银行卡、手机号和交易数据。

27.3 Data Masking

必须使用近似生产数据时，应进行不可逆脱敏或符合要求的匿名化。

27.4 环境污染

测试 A 创建、测试 B 依赖、测试 C 修改同一批共享数据，会造成不可复现。测试应具备隔离性。

27.5 Infrastructure as Code

环境应该可以通过 Docker、Kubernetes、Terraform 等方式重建，而不是依赖人工配置。

27.6 Ephemeral Environment

每个 PR 创建临时环境，测试后销毁，可显著提升隔离性。

27.7 Service Virtualization

对于银行、运营商、第三方支付等不可稳定调用的依赖，通过虚拟服务模拟成功、失败、超时和异常。

28. 测试策略、测试计划、Entry / Exit Criteria

28.1 Test Strategy

回答：测什么、不测什么、怎么测、谁负责、什么时候测、通过标准是什么。

28.2 Test Plan

包括范围、目标、人员、环境、工具、时间、测试类型、风险、入口条件和出口条件。

28.3 Entry Criteria

  • Build 成功。
  • Unit Test 通过。
  • 环境部署完成。
  • 测试数据准备完成。
  • 接口或需求定义达到约定状态。

28.4 Exit Criteria

  • P0 / P1 按规则清零或明确接受。
  • 核心回归通过。
  • 性能达到目标。
  • 关键安全问题关闭。
  • 核心业务链路通过。

28.5 Traceability Matrix

建立需求与测试用例的映射，避免关键需求遗漏。

29. 缺陷管理、RCA 与缺陷预防

29.1 Defect Lifecycle

New → Assigned → Fixed → Retest → Closed

也可能出现 Rejected、Duplicate、Deferred、Won't Fix。

29.2 Severity vs Priority

Severity：技术和业务影响有多严重。
Priority：多快必须修。

29.3 Root Cause Analysis

线上事故不应只修代码，还应追问为什么需求、设计、单测、集成测试、环境和监控没有提前发现。

29.4 Defect Prevention

Code Review、Static Analysis、Type System、Lint、API Schema、Architecture Rule 等都属于预防缺陷。

29.5 Production Bug Should Become Test

线上缺陷修复后，应考虑增加自动化回归测试，避免同类问题再次出现。

30. 质量指标与测试治理

成熟团队不会只看 Bug 数量，还会看：

  • Defect Escape Rate。
  • Regression Pass Rate。
  • Automation Coverage。
  • Flaky Rate。
  • MTTD。
  • MTTR。
  • Change Failure Rate。
  • Production Incident Rate。
  • 测试执行时间。

30.1 Defect Escape Rate

反映多少缺陷没有在测试阶段发现，而是进入生产。

30.2 Change Failure Rate

反映部署中有多少导致故障、回滚或紧急修复。

30.3 Flaky Test 治理

随机失败会让团队逐渐忽略 CI 红灯，最终测试体系失去可信度。常见原因有时间依赖、网络、共享数据、异步等待、动画、随机数、环境污染。

30.4 测试并行化与选择

通过并行执行、按代码影响选择相关测试、Risk-Based Regression 缩短反馈周期。

30.5 Fast Feedback

秒级：Static / Unit
分钟级：Component / API / Contract
十几分钟：Integration
小时级：E2E / Performance
持续：Monitoring / Chaos

31. 测试组织模式与 Quality Engineering

常见组织方式：

  • 独立 QA 团队。
  • 嵌入式 QA。
  • 开发自测。
  • SDET。
  • Quality Engineering。

SDET 更偏测试框架、平台、工具和自动化工程，而不是单纯执行手工用例。

现代趋势：从 “QA owns quality” 转向 “Team owns quality”。质量是产品、开发、测试、DevOps、SRE、安全共同责任。

31.1 测试四象限

Q1 技术 + 支持开发：Unit / Component
Q2 业务 + 支持开发：Functional / Story
Q3 业务 + 评价产品：Exploratory / Usability / UAT
Q4 技术 + 评价产品：Performance / Security / Reliability

31.2 测试金字塔不是绝对比例

不同架构还会讨论 Testing Trophy、Testing Honeycomb。核心仍然是：以最低成本、最快速度、最高稳定性发现最重要风险。

32. AI / LLM / RAG / Agent 系统测试

32.1 为什么传统 assert 不够

LLM 输出具有随机性和语言表达差异，不能总是简单做 output == expected。

32.2 LLM Eval 关注

  • 正确性。
  • 事实性。
  • 相关性。
  • 安全性。
  • 一致性。
  • 幻觉。
  • 延迟。
  • 成本。

32.3 Golden Dataset

准备典型问题、标准答案、危险问题、边界问题，每次模型、Prompt、RAG、工具链改变后重新评测。

32.4 Evaluation 方法

Human Evaluation、规则、Semantic Evaluation、LLM-as-Judge 等组合使用。

32.5 RAG 测试

把 Retrieval 和 Generation 分开测：是否找到正确材料，以及是否依据材料正确生成。

32.6 Agent 测试

需要覆盖 Planning、Tool Call、Memory、Execution、Recovery。特别要测试工具失败、权限不足、网络异常、重试、终止和恢复行为。

34. 风险驱动测试：测试资源永远有限

核心公式：

Risk = Probability × Impact

因此首页文案错误和重复扣款不应该获得相同的测试强度。关键资金、账务、授信、幂等、安全、可用性应获得更高优先级。

成熟测试设计的逻辑：风险 → 测试目标 → 测试方法 → 测试用例 → 自动化与质量门禁。

35. 架构师级测试思考框架

  1. 核心业务链路是什么？

  3. 有哪些外部与内部依赖？
  4. 关键状态有哪些？
  5. 哪些数据必须强一致或最终一致？

  10. 高并发下系统容量边界在哪里？

36. 最终形态：Quality Architecture

成熟体系不是“先开发系统，再补测试”，而是系统从设计开始就具有可验证性。

例如架构中主动明确：

  • 稳定且可版本化的接口。
  • 明确状态机。
  • 系统不变量。
  • 统一错误码。
  • TraceId / RequestId。
  • 幂等键。
  • 事务与一致性策略。
  • 可替换依赖。
  • 可注入故障。
  • 可观察性。

38. 一句话收束整套体系

不要再把测试理解成“开发完以后 QA 点点 App 找 Bug”。完整的软件质量体系应该持续回答：

需求是否正确？
架构是否支撑质量属性？
代码是否正确？
组件是否正确？
服务是否协作正确？
异常情况下是否仍然正确？
高并发下是否满足目标？
攻击情况下是否安全？
升级过程中是否兼容？
故障后是否能恢复？
上线后是否持续健康？

最终，测试从“发现 Bug”演化为：

通过需求、设计、架构、代码、自动化、测试、发布、监控和持续反馈，共同控制软件风险。
