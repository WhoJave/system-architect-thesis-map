01 · 先补底层概念

请求、事务与质量指标：后端为什么不能只看接口返回

01

一次点击后：请求、服务与数据库

API · HTTP · 同步调用 · 异步处理 · REST · gRPC

API 是约定好的入口；服务执行规则；数据库保存可持续恢复的业务事实。同步表示调用方等结果，异步表示先受理、稍后查询或通知结果。

展开图解、工程细节与论文表达
从前端经验出发

你熟悉 fetch / URLSession：界面等的是响应，后端还要访问数据库和其他服务。

携带身份、申请号和参数

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 借款按钮发送的是“申请借款”指令，不能由前端直接决定额度或账务金额。服务端要重新校验身份、参数和业务约束。
  2. REST 通常围绕资源设计 HTTP 接口；gRPC 使用明确的服务与消息类型进行远程调用。两者都面临网络超时、版本兼容和权限问题。
  3. 返回 HTTP 202 只表示已受理。App 可通过申请号轮询状态或接收通知，最终状态由服务端权威记录决定。异步不等于开一个线程后就可靠。

消费金融案例

授信审批耗时较长时，接口先返回申请号和处理中状态，App 展示进度；审批任务完成后更新权威状态。

适用边界与常见误区

同步链路短且延迟可控时更简单。异步增加状态查询、任务恢复和重复处理的治理成本。

理解之后，论文怎么写

针对外部核验耗时波动，我们将受理与审批执行分离，受理接口返回申请标识，由状态查询接口展示后续结果，避免渠道长时间占用连接。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：接口返回“已受理”，能否显示放款成功？

不能。已受理是流程起点，应查询资金处理的最终权威状态。

02

本地事务与 ACID：把一组修改绑在一起

本地事务 · ACID · 数据库事务 · 事务边界

本地事务在一个数据库事务范围内协调多条操作。ACID 分别强调原子性、一致性、隔离性和持久性。

展开图解、工程细节与论文表达
从前端经验出发

前端批量更新 UI 可能看起来同时发生，但数据库事务提供的是受控的提交与恢复语义。

建立本地事务

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 原子性：扣减可用额度与创建占用记录要么都提交，要么都回滚；避免只扣了额度却找不到原因。
  2. 隔离性：两个请求同时读到剩余额度时仍可能竞争，需要合适的锁、隔离级别或条件更新。ACID 的一致性主要依赖业务约束，不等于分布式 CAP 的一致性。
  3. 提交成功后的持久性仍要结合数据库配置、故障模型、备份和恢复策略理解。一个服务的数据库事务不能自动回滚另一个数据库或银行已经发生的操作。

最小实现骨架（教学伪代码）

BEGIN;
-- 伪 SQL：仅说明原子边界
UPDATE quota SET available = available - :amount
WHERE id = :id AND available >= :amount;
-- 必须验证受影响行数为 1，否则中止
INSERT INTO reservations(request_id, amount) VALUES (:request_id, :amount);
COMMIT;
省略了完整异常、并发与安全处理，不可直接用于生产。

消费金融案例

在额度服务内，用同一事务执行“校验并占用额度”和“写占用明细”，再向其他系统传播结果。

适用边界与常见误区

事务越长，锁持有时间越长。不要在数据库事务中等待长耗时网络调用；跨系统步骤需要额外协调。

理解之后，论文怎么写

我们将额度余额与占用明细纳入同一本地事务，通过条件更新防止并发超占，并将跨服务通知移出该事务边界。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：数据库回滚能撤销已经转出的银行款项吗？

不能。银行操作不在这个本地事务内，必须确认银行结果并采用业务恢复流程。

原理延伸：MySQL · InnoDB 与 ACID

03

质量属性：性能、可靠性、可用性与可扩展性

质量属性 · QPS · P95 · P99 · 可用性 · 可靠性 · 可扩展性 · SLO

质量属性说明系统“做得怎样”。性能看吞吐与时延；可用性看是否能提供符合约定的服务；可靠性看在规定条件下持续正确完成任务；可扩展性看增加资源是否带来容量提升。

展开图解、工程细节与论文表达
从前端经验出发

页面加载速度只是一个指标，后端还要保证请求结果正确、持续提供服务并能承受增长。

高峰申请可受理

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. QPS 是每秒请求数，响应时间是一次请求等待多久。并发数是同时在系统内的请求数量，不能混用三个指标。
  2. P95=某个阈值表示约 95% 的观测请求不超过该时延；它能揭露平均值掩盖的慢请求。样本范围、统计窗口和失败请求计入方式必须写清。
  3. SLO 是目标，不是口号。例如“某时间窗口内成功且满足时延标准的请求比例”。核心资金还需要金额正确性、重单率、未决交易等业务指标。

消费金融案例

为借款受理定义独立时延目标，并将资金正确性单独验证，避免“接口很快但重复放款”。

适用边界与常见误区

不能只报告平均响应时间或机器 CPU。示例值仅用于训练，应替换为实际测量结果与统计口径。

理解之后，论文怎么写

我们以受理成功率、P95 时延和未决交易恢复时长作为验收维度，通过压测和故障演练验证，而非仅比较 CPU 利用率。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：为什么平均响应快还会被用户投诉？

少量长尾请求可能很慢；需要 P95 / P99、超时率及分链路指标。

02 · 分布式缓存

快读背后的陈旧、回源与高可用

04

Cache-Aside：先查缓存，未命中再回源

Cache-Aside · Cache Aside · 回源 · 回填 · 数据库权威源 · 缓存客户端

旁路缓存模式由应用管理缓存：读时先查缓存，缺失时查询数据库并回填；写入权威源后使相关缓存失效。

展开图解、工程细节与论文表达
从前端经验出发

类似前端内存缓存请求结果，但 Redis 是独立后端服务，多台应用会共享它。

命中则直接返回；未命中往下

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. Key 可写为 product:{productId}:config:v2，值包含业务配置及版本。缓存客户端负责连接、序列化、超时与读写；数据源才拥有最终业务事实。
  2. 读命中时减少数据库访问；读未命中时仍要访问数据库。加缓存的目标是减少重复读，不是让数据库从此消失。
  3. 更新数据库后删除缓存是常见策略。删除失败、读写交错仍可能造成短暂旧值，需配合重试、版本和有界 TTL；此策略不是强一致协议。

消费金融案例

产品费率展示和公共字典高频读取且低频变更，适合缓存；扣额度和放款判断应按权威约束执行。

适用边界与常见误区

适合能接受有限陈旧的数据。不能拿缓存余额独立批准资金动作；缓存不可用时应限制回源量。

理解之后，论文怎么写

针对产品配置的重复查询，我们采用 Cache-Aside，将数据库作为权威源，并通过失效重试和 TTL 控制缓存陈旧窗口。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：缓存未命中是故障吗？

不是。它是正常路径，系统必须能在受控容量内回源和回填。

原理延伸：Microsoft · Cache-Aside（读写与陈旧窗口）

05

TTL、淘汰与序列化：三个不同问题

TTL · 淘汰 · 序列化 · Key 设计

TTL 是数据的存活期限；淘汰是在内存压力下按策略移除数据；序列化是对象与存储字节之间的转换。

展开图解、工程细节与论文表达
从前端经验出发

localStorage 不自动过期；后端缓存通常要同时管理新鲜度、内存上限和数据编码。

租户、对象、版本分隔

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. TTL 应与业务可容忍的旧数据时间匹配。加随机抖动能分散大批 Key 的到期时刻，但不会自动解决一个热门 Key 的重建争抢。
  2. 内存不足时，淘汰策略可能在 TTL 到期前移除 Key；某些策略也可能拒绝写入。即便 TTL 很长，也必须设计未命中路径。
  3. 序列化格式要处理版本兼容、字段缺省和金额精度。Key 区分环境、租户、业务对象与版本，不能混用客户之间的数据。

消费金融案例

公共字典可以设较长 TTL，营销产品配置按更新周期设较短 TTL，并用版本校验与主动失效协同更新。

适用边界与常见误区

TTL 是兜底，不是所有实时要求的解决方案；“永不过期”会积累陈旧数据和内存负担。

理解之后，论文怎么写

我们统一 Key 命名与序列化规范，按数据更新频率分层设置 TTL，并监测淘汰率，避免将自然淘汰误判为数据库异常。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：设了 TTL，数据是否保证一直保留到到期？

不保证。内存淘汰、主动删除和故障也会导致提前缺失。

原理延伸：Microsoft · Cache-Aside（读写与陈旧窗口）

06

穿透、击穿、雪崩：问题对象不同

穿透 · 击穿 · 雪崩 · 缓存穿透 · 缓存击穿 · 缓存雪崩

穿透是请求不存在的数据反复直达数据库；击穿是单个热点数据失效触发大量并发回源；雪崩是大量缓存同时失效或缓存服务故障引发广泛回源。

展开图解、工程细节与论文表达
从前端经验出发

把后端缓存想成前台资料架：不存在的资料、最热门资料缺失、整个架子不能用，后果各不相同。

不存在？一个热点？大量数据？

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 穿透：先做参数校验；对确定不存在的数据短暂缓存空值，必要时用布隆过滤器。布隆过滤器可能误报“存在”，不能替代数据库真值，还要维护新增数据。
  2. 击穿：可采用同一 Key 的请求合并、互斥重建、预热或逻辑过期。逻辑过期可以先返回旧值再刷新，只适用于允许旧值的场景。
  3. 雪崩：TTL 抖动减少批量到期，高可用与本地辅助缓存减轻影响；缓存整片不可用时仍需回源限流、熔断与降级。

消费金融案例

营销产品配置在高峰时单 Key 到期，属于击穿；不能只写“随机 TTL 解决了所有缓存问题”。

适用边界与常见误区

防护之间会有组合，但一定说明作用对象。空值缓存可能短暂遮住刚新增的数据，应设短 TTL 或主动失效。

理解之后，论文怎么写

我们区分穿透、击穿与雪崩：对不存在产品采用短期空值缓存，对热点配置合并回源，对批量失效采用 TTL 抖动与回源限流。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：一个热门产品 Key 到期，算哪一类？

击穿。核心原因是大量请求同时重建同一热点数据。

原理延伸：Microsoft · Cache-Aside（读写与陈旧窗口）

07

缓存一致性：更新与读取交错时会发生什么

缓存一致性 · 失效补偿 · 先更新数据库再删除缓存

缓存一致性要求明确权威源、更新传播方式和可容忍的旧值窗口。常见的先更新数据库再删除缓存并不自动消除所有读写竞争。

展开图解、工程细节与论文表达
从前端经验出发

前端刷新前页面仍可能显示旧值；多个后端实例同时读写会把问题放大到共享缓存。

缓存 miss，A 在数据库获取旧版本

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 设读请求 A 缓存未命中，在数据库读到旧值；写请求 B 随后更新数据库并删除缓存；A 最后才回填旧值，于是旧数据又出现。问题不是删除顺序错误，而是读写交错。
  2. 可按业务需要组合版本校验、更新事件、可靠失效重试、短 TTL 或受控延迟再次失效。每个方案都有假设；固定延迟不能无条件覆盖任意慢读。
  3. 若读结果决定扣款或额度批准，不能接受普通缓存陈旧语义，应回权威约束执行。展示型配置则可定义明确陈旧上限并测量失效失败率。

消费金融案例

营销费率配置允许短时间旧展示时，标记版本并设计失效恢复；借款实际签约必须再次使用有效权威规则确认，不能以展示缓存决定最终费率。

适用边界与常见误区

延迟双删等方案有时序假设，不能写成绝对强一致。越严格的正确性要求，越应缩小需要同步协调的权威事务边界。

理解之后，论文怎么写

我们以数据库作为配置权威源，分析读写交错与失效失败窗口，结合版本校验和可靠失效重试控制陈旧，并在签约时再次校验有效规则。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：数据库更新后删除缓存成功，还可能出现旧值吗？

可能。一个之前读到旧值的请求可能在删除之后才回填；必须分析并发时序。

原理延伸：Microsoft · Cache-Aside（读写与陈旧窗口）

08

HotKey、BigKey 与本地缓存

HotKey · 热 Key · BigKey · 大 Key · 本地缓存

HotKey 指访问极集中的 Key；BigKey 指值很大或成员很多的 Key。前者主要造成负载倾斜，后者增加传输、处理与删除成本。

CAP 讨论网络分区下无法同时保证线性一致性与该模型的可用性；BASE 强调在允许的场景接受暂时状态并最终收敛。

从前端经验出发

两个设备的本地状态短暂不同并不罕见；系统需要说明何时允许不同、怎样恢复一致。

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. CAP 的 C 通常指线性一致性：操作看起来像在一个顺序中即时生效；A 指每个到达非故障节点的请求得到响应，不能简单等同服务月可用率。
  2. 网络分区发生时，需要对受影响操作选择等待 / 拒绝或允许各侧处理。这不是平时可以随意从 C、A、P 选两个的口号。
  3. 最终一致的前提包括更新传播、错误恢复以及冲突处理；若消息一直失败且没有修复，并不会“时间长了自然一致”。资金不变量与通知状态可采用不同边界。

同一额度账户禁止并发超占，优先在权威事务边界保证；短信与分析视图允许延迟，但要有可观测的恢复路径。

TCC：预留、确认、取消

TCC · Try · Confirm · Cancel

TCC 将每个参与方的业务拆成 Try 预留资源、Confirm 确認使用和 Cancel 释放预留，由协调逻辑推进最终决议。

展开图解、工程细节与论文表达
从前端经验出发

类似先占一个限量预约名额，最终确定再确认，不确定之前不直接当作已完成。

冻结额度，保存分支状态

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 额度可从“可用”转到“冻结”。Try 成功只说明资源已经被预留，不是资金动作已完成。Confirm 与 Cancel 需要可重复执行。
  2. 协调方可能在决议后失败，必须持久记录状态并重试未完成分支。业务需处理空回滚、悬挂：Cancel 到达早于 Try 或取消后迟到 Try 的情况。
  3. TCC 在业务层显式实现资源约束，侵入性与运维成本较高。它不会自动让未提供预留接口的银行操作拥有 TCC 语义。

消费金融案例

借款准备流程如果参与方支持资源预留，可在确认合同等条件后确认冻结额度；外部资金通道仍按它自身协议处理。

适用边界与常见误区

TCC 不等于全程持有数据库锁，也不自动提供全局串行隔离。预留资源可见性和业务不变量要显式设计。

理解之后，论文怎么写

对支持资源预留的步骤，我们设计 Try / Confirm / Cancel 接口，持久记录协调状态，并通过幂等与防悬挂控制迟到调用。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：Try 成功是否意味着借款已经完成？

不是，Try 只是预留，最终决议与各方确认仍需完成。

原理延伸：Apache Seata · TCC 模式

Saga 与补偿：已提交步骤的业务恢复

Saga · 补偿 · Compensation · 编排 · 协同

Saga 将长业务流程拆成多个已提交的本地事务。后续失败时，对可补偿步骤执行新的业务动作以恢复可接受状态。

展开图解、工程细节与论文表达
从前端经验出发

前端多步骤向导按次提交，后续失败时前面已保存的内容不会被浏览器“自动撤销”。

创建业务对象

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 补偿不是数据库回滚：原记录已提交，补偿会创建新的记录或状态变更。退款也不是让历史付款从未发生。
  2. 编排式由协调器追踪步骤；协同式由服务响应事件推动。前者便于看全流程，后者需治理事件依赖和循环，二者都有成本。
  3. 补偿可能失败，必须记录并重试；已发生且不可逆的外部动作不能假装取消。Saga 的中间状态可能被其他流程看到，需要语义锁或状态检查。

消费金融案例

若合同准备确定失败且资金尚未执行，可取消申请、释放预占额度。若银行已成功放款，不能直接使用同一补偿路径。

适用边界与常见误区

Saga 通常不具备全局隔离；补偿须结合业务事实和法律操作约束，结果未知时先确认再恢复。

理解之后，论文怎么写

我们将长流程组织为多个本地事务，通过持久化编排状态控制步骤推进，确定失败后执行可重复的业务补偿，并跟踪补偿未完成事项。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：补偿成功后，历史动作是不是从未发生？

不是。历史仍保留，恢复通过新的业务动作和状态完成。

Outbox、CDC 与事务消息：解决双写窗口

Outbox · CDC · 事务消息 · Transactional Outbox · 双写

Outbox 在同一本地事务里保存业务数据和待发布事件，再由中继可靠投递。CDC 可从数据库变更日志捕获已提交的事件记录。

展开图解、工程细节与论文表达
从前端经验出发

前端“先保存表单，再发通知”两步中间断网，可能保存了却没通知；后端 DB + MQ 双写也有这个窗口。

业务表与 Outbox 同时写

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 业务和 Outbox 行一同提交，避免“业务提交但根本没有可恢复的事件记录”。中继仍可能发布成功却来不及记录进度，因此消费者需幂等。
  2. 轮询发送器与 CDC 都可做中继；轮询更直接，CDC 减少轮询但增加日志位点、连接器和运维治理。事件内容包含稳定 ID、业务对象 ID 与版本。
  3. 事务消息是某些 MQ 产品提供的机制，例如结合半消息和事务回查协调发布。不同产品协议不同，不能当成所有 MQ 统一自带的数据库分布式事务。

最小实现骨架（教学伪代码）

BEGIN;
UPDATE loan SET status = :confirmed_status WHERE id = :loan_id;
INSERT INTO outbox(event_id, aggregate_id, payload)
VALUES (:stable_event_id, :loan_id, :event_json);
COMMIT;
-- 中继另外发布：可恢复、可重复，下游必须幂等
省略了完整异常、并发与安全处理，不可直接用于生产。

消费金融案例

记账成功后需通知贷后系统，事务内写入账务记录和 Outbox 事件，中继恢复后继续发布，避免临时 MQ 故障丢失通知。

适用边界与常见误区

Outbox 保障业务状态与待发事件记录的原子性，不是所有下游一瞬间一致；还需中继恢复、幂等、顺序与积压治理。

理解之后，论文怎么写

我们以 Outbox 将账务更新与待发事件纳入同一本地事务，通过中继重试实现可恢复发布，下游以事件标识去重。

这是表达训练示例。角色、措施和效果需对应自己的真实经历；不可把教学案例写成已经实施的事实。
先回答：Outbox 是否消灭重复消息？

没有。中继可重复发布，消费端仍需幂等。

原理延伸：Debezium · Outbox Event Router · Apache RocketMQ · 事务消息与回查

未知或差异交易

Entity 与 Value Object：身份和属性的区别

Entity · 实体 · Value Object · 值对象

实体靠稳定身份识别；值对象靠属性值表达含义，通常设计为不可变。身份决定“是谁”，值决定“是什么值”。

展开图解、工程细节与论文表达
从前端经验出发

前端列表的 key 标识同一个对象，即使名称变了还是它；两个相同数值则可能完全等价。

以借据号追踪生命周期

概念关系图：连线表示归属或协作，不表示执行先后。

把原理拆开

Aggregate 与 Aggregate Root：守住不变量的入口

Aggregate · 聚合 · Aggregate Root · 聚合根 · 不变量

聚合是一组需要共同维护业务不变量的对象；聚合根是外部访问与修改这组对象的受控入口。通常让一个聚合的变更在一个事务边界内完成。

展开图解、工程细节与论文表达
从前端经验出发

业务修改的受控入口

概念关系图：连线表示归属或协作，不表示执行先后。

把原理拆开

  3. 聚合是模型与一致性边界，不是一张表或一个微服务。跨聚合协作通常使用标识引用与事件，具体事务策略仍取决于真实业务要求。

Human-in-the-loop：执行前审批与审计

Human-in-the-loop · HITL · 人工确认 · 调用上限 · 防止死循环

人在回路通过审核、纠正或批准控制执行。高风险工具动作应将具体动作、参数和权限与审批结果绑定。

展开图解、工程细节与论文表达
从前端经验出发

像提交付款前的确认页，但确认内容应固定，不能确认后让模型偷偷改金额或对象。

明确对象、参数与影响

流程示意：正常与异常条件见节点说明，实际方案还需完整业务判断。

把原理拆开

  1. 审批展示对象、动作、影响与关键参数，授权一次具体执行，不是批准“之后所有动作”。确认后参数变化应重新校验。
  2. 执行必须有幂等标识、有效期与权限复核。人工确认并不会消除工具故障、重复投递或外部结果未知的问题。
  3. 若预算耗尽、步骤循环或工具持续失败，停止并移交，保留上下文和已执行事实。审计能说明誰批准、执行了什么及实际结果。
