主线 · 用同一案例串知识

一条案例题的完整推理链

为什么这些知识必须一起学？因为考试往往要求从需求推导架构，而不是单独背术语。

贯穿案例（教学示例，非原书真题）：某消费金融平台在大促期间出现响应变慢、数据库压力过大；故障切换慢；新风控规则上线周期长；需要接入外部银行的异构系统。架构团队准备重新设计。
① 认质量慢 → 性能；切换慢 → 可用性
→
② 写场景谁 / 触发 / 状态 / 对象 / 行为 / 指标
→
③ 找影响敏感点、权衡点、风险
→
④ 评方案ATAM / 效用树
→
⑤ 选技术SOA、云原生、Redis

记忆锚点：“认—写—辨—评—选”（本页面自编学习法）。碰到新案例，按此顺序组织答案。

02 · ★★★★★ SUPER IMPORTANT

九大质量属性 · 判题训练台

先读“题干信号词”，再说定义，最后补相应设计策略。

原书 p100–105
九大属性的地图

点击任意格子切换。性能看“多快”；可用性看“不中断 / 多快恢复”；可修改性看“改动代价”；安全性看“防护、审计”。

容易混淆：原书把可靠性、可用性分开列出，也提醒真题常将故障切换归入可用性。当题目明确同时出现两者时，应结合其措辞细分，不要机械认为完全相同。
03 · ★★★★★ SUPER IMPORTANT

六要素场景 · 从“抽象词”写成“可验证句子”

把质量目标变成具体场景，考试会要求填空、辨认六要素、或按模板写出场景。

原书 p105–111
原书六要素：刺激源 → 刺激 → 环境 → 制品 → 响应 → 响应度量。
自编速记：“谁来、做啥、啥时候、作用谁、怎么做、量多少”。
特别注意：刺激是“发生的事件”；环境是“事发时的系统状态”；响应是“系统采取的行为”；度量是“可检验的数字或指标”。

六要素组装器 动手练

选一个场景作为起点，修改每个要素，自动生成一段结构完整的案例答案。

填写六要素后，点击“生成完整表述”。
答题细节：原书 p107 建议将六要素先分成“触发侧”和“响应侧”记忆。不要把“采用 Redis”直接写成响应度量；“99% 请求在 200ms 内完成”才是可量化的目标（此处数值为演示设定）。
04 · ATAM FOUNDATIONS

敏感点 vs 权衡点 vs 风险点

辨析的核心：影响一个质量目标、同时影响多个质量目标，还是有潜在失效风险。

原书 p111–113
敏感点 · Sensitivity Point

改一个参数，质量表现变化明显

某个架构决策或构件特性对一个或多个质量属性敏感。考场先看“该设计的变化影响了什么质量”。

例：数据库连接池容量对并发请求处理时间很敏感。
权衡点 · Tradeoff Point

一项设计同时牵动多个质量属性

多个质量属性存在彼此冲突或需要平衡的效果。是“性能提高但安全下降 / 安全加强但开销增加”。

例：加密算法与加密措施会影响安全性，也可能影响性能。
风险点 · Risk

某决策可能使目标达不到

不是有代价就一定是风险。要有“可能导致目标不能实现”的判断依据。

例：只有单个 Redis 主库且无故障转移，可能无法满足故障恢复时间要求。

互动：架构的性能 / 安全权衡

拖动“校验与防护强度”，观察定性权衡。此模型只用于记忆，不预测真实性能数值。

安全校验强度中等
基础校验强化校验多重校验

观察结果

安全性 ↔ 性能权衡点
精确区别：敏感点强调“架构决策对质量属性敏感”；权衡点强调“同一决策跨多个质量属性”。二者并非互斥，权衡点往往涉及多个敏感点。
05 · ★★★★★ ATAM

ATAM · 质量效用树的操作流程

考场两种能力：会认“树的结构”，能把业务要求归入四大质量属性。

原书 p113–117
ATAM 是什么：架构权衡分析方法（Architecture Tradeoff Analysis Method）。在架构设计阶段围绕质量属性进行评估与折中；教材强调 性能、可用性、安全性、可修改性 四类，利用效用树与场景分析识别风险、敏感点和权衡点。

06 · ★★★★★ SOA / ESB

SOA · 把异构银行系统变为可调用的服务

记住角色与流程，再区分 UDDI、WSDL、SOAP、ESB 和微服务。

原书 p76–87
服务提供者Provider · 提供能力
→
服务注册中心UDDI · 服务目录
←
服务请求者Consumer · 找到并调用

① 提供者发布服务 → ② 请求者查找 → ③ 获取接口描述并调用

UDDI

服务在哪里？目录发布 / 查询 / 发现。

WSDL

接口怎么用？描述操作、参数、绑定等。

SOAP

消息怎么交换？基于 XML 的消息协议。

ESB

异构系统怎么通？路由、协议和格式转换、监控。

SOA 原书口诀：无单明自粗松重互 → 无状态、单一实例、明确定义的接口、自包含和模块化、粗粒度、松耦合、重用、互操作性等。

SOA、微服务、单体：判场景的五个维度

维度SOA微服务单体
粒度通常较粗，企业业务服务更细，按业务能力拆分统一应用内部模块
交互标准契约；SOAP 等轻量接口 / 消息主要进程内调用
集成可用 ESB 统一治理倾向分散治理/服务网格整合在单体应用内
部署服务可独立部署独立开发、部署、扩容整体打包部署
优点/代价异构集成强；总线可成瓶颈灵活；分布式治理复杂简单；后期改动牵连大
区分现实与教材简化：SOA 不一定必须有 ESB，微服务也不保证“系统复杂度整体更低”。原书该表格着重表现服务内部独立性；实际微服务的运维与分布式协作复杂度可能更高。
07 · ★★★★★ CLOUD-NATIVE

云原生 · 从能运行到能自动治理

考点包括七原则、七模式、容器和虚拟机的关键区别。

原书 p68–75
七原则（自编首字记忆）：“服弹观韧自零续”
服务化、弹性、可观测性、韧性、全流程自动化、零信任、持续演进。
必辨：弹性应对业务负载波动；韧性应对系统故障和异常。

容器 / 虚拟机 / 编排的角色

Docker · 容器

装应用

应用及依赖打包；共享宿主内核。启动快、资源较省、隔离弱于独立内核虚拟机。

虚拟机 · VM

装完整系统

虚拟化硬件，每个虚拟机可运行自己的操作系统内核。更重、隔离边界相对更强。

Kubernetes · 编排

管很多容器

负责调度、声明式部署、自愈、服务发现与弹性伸缩；不是替代容器。

在消费金融大促中：流量突增用自动弹性扩容；节点异常用健康检查、重启/故障转移；排查延迟用日志 + 指标 + 链路追踪。三个目标分别对应弹性、韧性、可观测性。
08 · ★★★★★ REDIS

Redis · 高频案例的故障判断与方案选择

选数据类型、选部署模式、辨缓存问题、保障一致性、解释事务。

原书 p192–211

缓存穿透 / 击穿 / 雪崩：三个图景

用户请求并发流量
→
RedisCache
→
DB数据库
—

三种部署方式：先分清“高可用”和“扩容”

主从复制复制数据

主写从读、数据冗余；单纯主从不提供 Sentinel 那样的自动故障转移。

哨兵 Sentinel故障自动切换

检测异常 → 选哨兵 Leader → 选新主 → 重建复制 → 旧主恢复后变从。

Redis Cluster分片 + 高可用

16384 槽分配给多个主节点，支持横向扩展与主从自动故障转移。

关键判题句：“不够存、需要水平扩展” → Cluster；“容量够但不能宕” → 主从 + Sentinel。这是教材 p201–202 的对比要点。

数据库缓存一致性

更新数据库
→
删除缓存
→
下次读请求
重新回填

Cache Aside（缓存旁路）常见写路径；不能宣称任何并发时序下都严格一致

RDB vs AOF

RDBAOF
某时刻的数据快照追加写命令日志
恢复快、文件相对紧凑可选择更高写入持久频率
快照间隔内可能丢数据追加 / 重写机制带来开销

Redis 事务 超级重点

MULTI 入队 → EXEC 顺序执行；DISCARD 取消队列；WATCH 可用于乐观锁检查。

与传统关系型数据库事务不同：运行时某条命令失败通常不回滚已经执行的命令；持久性取决于 RDB/AOF 设置。
展开：Redis 常考数据类型速记

String：计数/简单缓存；Hash：对象字段；List：列表队列；Set：去重/交并集；ZSet：排行榜；Bitmap：位状态；HyperLogLog：近似去重计数。出处 p192–193。

展开：全量同步 5 步、哨兵故障切换 4 步

全量同步：PSYNC 握手 → 主库 BGSAVE 快照 → 传输并加载 RDB → 补发复制缓冲中的写命令 → 常态增量复制。
哨兵切换：选出哨兵 Leader → 选新 Master → 重建主从并通知客户端 → 旧主恢复后降级为从库。出处 p195、198–199。

展开：分布式锁 / 布隆过滤器 / 热 Key、大 Key

锁：数据库锁表、Redis / Redisson、ZooKeeper 临时顺序节点；关注互斥、过期、可重入和主从切换的可靠性。
布隆过滤器：位数组 + 多个哈希函数，可判定“一定不存在”或“可能存在”，存在假阳性。
热 Key：流量集中，考虑本地缓存、分散读压力、业务隔离。大 Key：数据量/成员数过大，考虑拆分、清理、调整存储。出处 p205–209。
